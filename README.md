# 随境(AnyContext)

> 一个通用的上下文驱动框架，可作为企业或机构的基座平台，也可作为集成与分发的节点。
>
> 源自 MedContext（医境）模型，去掉特定行业语境后的通用化版本。

---

## 架构简述

本项目探索一种**事件驱动**的上下文驱动框架：以「事件」为最小管理单元，而非以表单或岗位动作为中心。它可以作为企业或机构的**基座平台**，也可以作为**集成或分发的节点**，接入更广泛的工作流生态系统。

### 主线

实体 → 事件 → 流程 → 处置（意图 / 行为）

### 分层

| 层级 | 核心对象 | 职责 |
|---|---|---|
| 实体层 | 基础元数据，如人员信息，设备信息，空间信息等
| 事件层 | 事件（时间 / 地点 / 人物 / 额外属性） | 捕获发生了什么 |
| 流程层 | 流程、节点 | 决定走哪条路，承载上下文 |
| 处置层 | 处置目标、处置行为、角色与个体 | 决定做什么、做到什么状态 |
| 分析层 | 数据池、分析报告 | 人工 + AI 的二次分析 |
| 决策层 | 决策者、决策流程 | 调整流程结构、响应级别与资源 |

### 关键设计

- **事件多维标注**：空间（公开 / 公共 / 半公共 / 企业内部）、时间（上班下班、工作日节假日、白班夜班）、人物（核心业务人员 / 服务对象方 / 后勤外包与驻场）。地点与时间属性直接决定流程与处置目标的差异。
- **多重角色**：同一个人同时承载专业身份、员工身份、普通人身份等，事件支持多角色标注，角色影响后续流程与处置。
- **智能匹配**：一个事件可并行触发多个流程、链式触发多个连环事件，减少对人工判断"该走哪个流程"的依赖。
- **大流程不切割**：外部人员（服务对象、家属、外包）的动作作为节点嵌入大流程，避免流程被切碎导致上下文丢失。
- **有限状态机**：每个处置目标都有可枚举、可判定、可归档的状态机。
- **双层兜底 + 培养池**：流程层「其他流程」、处置层「其他处置」承接无法归类的情形；兜底实践中的重复模式被沉淀为新的规范流程与角色。
- **流程间切换**：流程之间存在响应度、密集度、升级/降级关系，可用一个流程完成另一个流程的暂停与承接。
- **决策回归流程**：分析任务对应分析流程，决策任务对应决策流程；决策流程属于"流程的流程"，具有启动—落地—验收的项目管理特征。
- **隐形上下文工程**：事件、人、事物、流程作为实体，维护"流程↔人""事件↔人"等多维双向关系；上下文被系统化维护后，AI 可按需调取而无需重新拼接。

### 物理部署架构

框架支持灵活的物理部署策略，适应不同规模与合规要求的组织场景：

- **物理分池设计**：事件层在物理层面可划分为多个独立的池（Pool），每个池与特定的内部流程域、高频流程或高频事件域强关联（如核心业务事件池、后勤运维事件池、客户服务事件池）。
- **数据总线与聚合**：各物理分池通过数据总线（Data Bus）或消息队列等技术互联，最终聚合为统一大池（Unified Pool），负责事件跨池广播、流程状态同步、全局查询聚合。
- **多实例部署**：支持部署多个独立实例（每个实例拥有完整的事件层、流程层、处置层），适用于过渡期隔离、安全审计隔离、多部门/多法人实体、灾备与高可用等场景。
- **全局聚合与统一视图**：尽管各实例物理独立，但通过聚合层实现跨实例流程合并唤醒、全局交流协作、统一视图，形成"物理分散、逻辑统一"的架构。

### 作为集成/分发节点

Any Context 不仅可作为独立的基座平台运行，还设计为可嵌入更大生态的**集成节点**：

- **事件桥接**：通过标准事件接口与外部系统对接，将外部系统产生的事件纳入本框架的事件流
- **流程桥接**：通过流程适配器与外部工作流引擎互联，实现跨系统流程的唤醒与状态同步
- **数据分发**：归档后的上下文数据可通过数据总线分发到下游分析系统、BI 平台或 AI 服务
- **多租户支持**：不同组织或业务单元可作为独立租户运行，共享底层框架能力但数据隔离

### 上下文实体关系

```
实体 ↔ 事件 ↔ 人(角色/个体) ↔ 流程 ↔ 事物

双向关系：
- 一个流程有多少人参与
- 一个人参与了多少流程
- 一个事件涉及了多少人
- 一个人涉及了多少事件
```

这些多维双向关系被系统化维护后，AI 介入时即可按需调取上下文，无需刻意重新拼接——这是**上下文工程的一种隐形实现方式**。
